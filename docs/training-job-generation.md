# Phase 11 LlamaFactory job generation

Phase 11 creates a reviewable external training-job bundle; it does not execute training. Every job is department-scoped and starts from one exact succeeded, approved, unpurged Phase 10 dataset. `system_admin` and `department_admin` may enqueue, cancel, and review jobs only within their department. `system_admin`, `department_admin`, and `instructor` may read safe metadata. There is no cross-department bypass and no artifact, dataset, configuration, download, or raw-argument endpoint. A future Phase 12 adapter may record this exact succeeded job as verified governance lineage, but that association is not proof that an untrusted external environment used the bundle or executed the declared training.

The fixed contract is LlamaFactory `0.9.5` with `Qwen/Qwen3-0.6B` at immutable revision `c1899de289a04d12100db370d81485cdf75e47ca`, Apache-2.0. The fixed profiles are `phase11-qwen3-0.6b-lora-v1` and `phase11-qwen3-0.6b-qlora-nf4-v1`. Both set `packing: false`, `neat_packing: false`, `enable_liger_kernel: false`, and `use_unsloth: false`, as well as SFT, `qwen3_nothink`, disabled thinking, a 8,192-token cutoff, deterministic seeds, and no remote code. QLoRA adds only reviewed NF4 four-bit settings: `quantization_bit: 4`, `quantization_method: bnb`, `quantization_type: nf4`, and `double_quantization: true`. `bnb` is the reviewed LlamaFactory enum value for its bitsandbytes backend; deprecated `use_liger_kernel` and `quantization_method: bitsandbytes` are never emitted. The normal worker never downloads or loads model/tokenizer bytes and CI does not install LlamaFactory. Two compatibility smokes are explicitly opt-in through `DEPTSLM_RUN_LLAMFACTORY_CONFIG_SMOKE=1` in a separately provisioned environment. They use only LlamaFactory 0.9.5's strict `_parse_train_args` parser path; normal CI defines and skips them and does not claim that the pinned parser executed.

The immutable bundle is `manifest.json`, `training.yaml`, `dataset_info.json`, `train.jsonl`, and `validation.jsonl`. Enqueue records the complete closed Phase 10 authority snapshot: source bundle and build identity, status/review/version, publication identity, code and artifact contracts, manifest/file digests and sizes, and all reviewed counts. Initial load and final locked authority revalidation compare every snapshot field. The parent retains exact verified Phase 10 file descriptors through final PostgreSQL authority; the child receives those descriptors directly and never reopens a source by pathname. Train and validation records are validated and copied through bounded buffers, while provenance is streamed only for identity and digest verification. Files are written only to private descriptor-relative staging, atomically renamed, and rehashed before PostgreSQL receives content-free digests, counts, contracts, lifecycle state, and review metadata. PostgreSQL and external storage are not transactional; only a committed succeeded job is authority for review.

Reconciliation and retention purge are explicit, bounded, department-scoped operations. A succeeded job has exactly one physical final bundle surface, keyed by department and training-job UUID, even though attempts retain distinct stage paths. Purge registration locks each selected job and every terminal attempt, validates one exact succeeded owner against the closed job and attempt manifests, records unresolved exact stage surfaces, records exactly one authoritative final surface, and commits a durable job-level reservation containing the expected version, review status, server-time retention anchor, retention period, exact succeeded publication attempt, closed content-free owner manifest, and UUID tombstone identity. A historical attempt never authorizes or tests the current final path.

A second authorized transaction revalidates the complete owner and reservation before stage cleanup. Only after every stage item is complete does it durably transition the reservation to `deletion_authorized`, revalidate the exact owner again, and verify the full final bundle before an atomic no-replace move into a private UUID tombstone below `.deleting/jobs`. Both parent directories are fsynced. The UUID is a namespace key, not filesystem identity: before any cleanup, a `tombstone_bound` reservation commits the exact private directory, parent, and five fixed-file identities (device, inode, UID, mode, link count, size, and timestamps). Each unlink has a durable in-flight record; a retry accepts a missing file only for that exact interrupted unlink and compares every remaining member and parent identity before touching it. A parked, replaced, partial, or same-UID substituted tombstone remains fenced. A pre-move manifest or ownership failure blocks with the final intact. Once moved, a cleanup interruption keeps the same reservation and item active for exact resumable cleanup rather than terminalizing it. An unbound absent final/tombstone pair is never evidence of deletion; only an already bound absent tombstone is idempotent completion. One durable purge operation increments each purged job once and emits at most one `training.job.purge` success audit after all active reservations close. Empty apply runs create no operation, reservation, item, or audit. Review and archive changes reject while a reservation is active. Purge never deletes Phase 10 dataset artifacts or claims deletion from backups or audit history.

Worker leases use PostgreSQL server time. Stale cleanup, dataset authority loading, retained-descriptor hashing, stage preparation, child execution, attempt registration, marker transition, rename/durability, post-rename hashing, and publication registration each receive a fresh parent deadline, heartbeat, cancellation, shutdown, and claim-loss guard. The parent uses another fresh guard to renew immediately before the short final metadata transaction; after that transaction starts it performs only local shutdown/deadline checks and validates the exact lease in that same transaction. It never opens a nested lease-renewal transaction while final row locks are held.

No question, instruction, answer, provenance, filename, path, model output, vector, training log, model weight, adapter, token, or credential is persisted in PostgreSQL, public responses, audit events, logs, or the browser. Phase 11 does not install or invoke LlamaFactory, run a scheduler, create training logs, produce adapters, promote a model, or implement Phase 12.1A's static contract or Phase 12.1B through 12.4. A future adapter retention dependency fences purge of this exact job and dataset until the registry artifact and every bound import-source copy are committed purged; Phase 11 purge never deletes them itself.
